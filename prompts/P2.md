## 2 — The canonical printer

> Next unit: the printer only. Do not touch the evaluator and do not write the
> equation predicates yet.
>
> Implement the assignment's canonical form exactly. Restating the rule:
> `*` and `/` bind tighter than `+` and `-`; operators are left-associative; a
> **left** operand is parenthesised only if its top operator has **lower**
> precedence than its parent's; a **right** operand is parenthesised if its top
> operator has the **same or lower** precedence than its parent's; a single
> number is never parenthesised. No spaces anywhere. The result must be an
> SWI-Prolog **string**, not an atom and not a code list.
>
> Note the left and right rules are deliberately asymmetric — that is what makes
> `1+2+3` and `1+(2+3)` print differently. Write it so a single number simply
> has no parenthesising clause, rather than special-casing it with a cut.
>
> Then check your renderer against every example in the assignment —
> `(4+2)*3`, `4+2*3`, `8/4*2`, `8/(4*2)`, `1-2-3`, `1-(2-3)`, `1+(2+3)`,
> `1+2+3` — by building each tree by hand and printing it. Show me the full
> table of expected versus actual.

## 3 — P2.a, `generate_equation/2`

> Next unit: P2.a only.
>
> Define an `equation/2` helper that enumerates one valid equation string for a
> list: split the list into a non-empty prefix and a non-empty suffix, build an
> expression over each side, require both sides to have the same value, render
> both and join them with `=`.
>
> Express "both sides are equal" by sharing one variable between the two
> `expression/3` calls, not by computing two values and comparing them
> afterwards.
>
> Then define `generate_equation(List, Equation)` on top of it, giving one valid
> equation. It must **fail** — not loop, not raise — when none exists, including
> for lists of length 0 and 1. Explain in the comment why it terminates for
> every input.
>
> Make it deterministic, but make sure it still works when `Equation` is already
> bound, so it can be used as a check. Show me that
> `generate_equation([4,2,5,3], E)` succeeds, that `generate_equation([2,3,4], E)`
> fails, that `[]` and `[7]` fail, and that passing a known-valid string as
> `Equation` succeeds while a bogus one fails.
>
> Do not build a string and parse it back to evaluate it at any point.

> Next unit: P2.b only.

> `count_equations(List, N)` as the length of that list. Both deterministic.
>
> Say in the comment which step is the one that removes duplicates, and why
> `sort/2` rather than `msort/2`.
>
> Then verify against the assignment's worked examples and show me the raw
> output:
>
> - `all_equations([4,2,5,3], Es)` must give exactly
>   `["4*2-5=3", "4*2=5+3", "4-2=5-3", "4/2=5-3", "4=2*(5-3)", "4=2+(5-3)", "4=2+5-3"]`

> - `all_equations([2,4,8], Es)` must give `["2*4=8"]`.
>
> If the order differs from the assignment's, work out whether the problem is
> the sort or the renderer before changing anything.
